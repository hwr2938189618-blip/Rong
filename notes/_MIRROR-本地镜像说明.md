# 本地镜像说明与"推送成功"的验证方法

> **日期**: 2026-09-16
> **标签**: #GitHub #镜像 #验证方法 #踩坑
> **状态**: 🟢 已整理

## 我要解决什么问题

本机有三处"仓库的本地痕迹"，但**没有一处是完整克隆**，容易把"本地看起来对"误当成"远端就是这样"。这篇把它们的性质说清，并给出验证推送结果的正确方法。

## 三处本地痕迹

| 位置 | 性质 | 能用吗 |
|---|---|---|
| `E:\DSH\workspace\Rong` | DSH 侧的**部分文件副本**，无 `.git` | ⚠️ 只能当草稿本，**不能当真相** |
| `E:\workbuddy文件夹\2026-09-12-13-13-38\Rong-repo` | WorkBuddy 侧的快照，实测**也没有 `.git`**（且内容更旧） | ⚠️ 不可作为同步源 |
| 远端 `api.github.com` | **唯一权威来源** | ✅ 一切验证都以它为准 |

> 关键：**三者都可能是旧的或不全的**。做完整性判断必须问远端。

## 正确验证"推送是否成功"

不要用本地文件数/字节数判断远端状态（会被"镜像不全"误导）。按这个顺序：

1. `get_file_contents` 读远端目录 → 确认文件清单
2. 对关键文件比对远端 `size` 字段与本地字节数
3. `list_commits` 确认 commit 存在、且**父提交是你预期的那个**（防止覆盖了别人的提交）
4. 导航类文件（`notes/README.md`）额外核对：**分类计数 == 该目录实际文件数**

```text
典型误判：本地 toolbox 只有 5 个文件，但导航写 7 → 以为导航错了。
真相：远端就是 7 个，是本地镜像缺了 2 个。
```

## 踩坑记录

| 问题 | 原因 | 解决 |
|---|---|---|
| 用本地文件数校验导航计数，报"不一致" | 本地镜像是部分副本 | 校验对象应是**远端目录清单**，不是本地 |
| 以为 WorkBuddy 那个目录是 git 仓库可直接同步 | 它没有 `.git`（快照而已） | 不做本地同步，按需从 API 拉 |
| 以为"后推的会报冲突" | MCP/REST 是无条件写 | 先读最新版再改，见 [多 AI 共写仓库防冲突方案](toolbox/07-多AI共写仓库防冲突方案.md) |
