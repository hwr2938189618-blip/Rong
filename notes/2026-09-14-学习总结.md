## 2. 程序数据搬家：目录联接（Junction）

**问题**：C 盘紧张，但程序的配置/数据目录写在 C 盘，直接搬走程序就找不到。

**做法**：搬走真实文件，在原位置留一个**目录联接**指向新位置。

```
C:\Users\29381\.codex                        →  D:\codex\.codex
C:\Users\29381\AppData\Local\OpenAI\Codex    →  D:\codex\app-runtime
```

对程序来说**路径一个字节都没变**（配置文件里的绝对路径不用改），但真实数据全在 D 盘，
以后新产生的数据也自动落 D 盘。本次从 C 盘释放 **1.17 GB**。

**验证方式**：不是"看图有没有"，而是**真的把程序跑起来** ——
`codex.exe --version` 返回 `codex-cli 0.153.4`、退出码 0。

→ 详见 [windows/02-目录联接搬数据.md](../windows/02-目录联接搬数据.md)

## 3. DSH：一个插件就能拖垮整个界面

今天最大的教训。DSH 的插件是**双半结构**（host 半跑在 Node，client 半跑在浏览器），
三个条件缺一个，**不是那个插件失效，而是整个界面打不开**：

| 坑 | 触发条件 | 表现 |
|---|---|---|
| A | git 源仓库只有 TS 源码、不提交构建产物 | `Cannot find module .../lib/index.js` |
| B | client 半注册的 id ≠ 包名 | `Failed to load plugins`（整页） |
| C | 包没声明 `dsh.bundle.patch` | 装上了但不激活，静默失效 |

**最关键的一条认知**：坑 B 发生时 **host 日志是干净的**，报错只出现在渲染进程。
我一开始只盯 `logs\host\*.log`，完全查不出来。

→ 详见 [dsh/01-插件双半结构与加载失败.md](../dsh/01-插件双半结构与加载失败.md)

## 4. DSH 的写锁：孤儿锁为什么能永久堵死启动

DSH 启动要拿一把写锁，而这把锁的设计是：

- 用 `wx` 独占创建 `<名字>.lock`，**里面写的是持有人 PID**
- 只等 **2000 毫秒** 就放弃
- **永不自动清理** —— 源码原话：*"orphan recovery is an operator action"*

所以**占锁的进程被强杀（崩溃 / 任务管理器结束 / 超时掐断），锁会永久留在原地**，
之后每次启动都失败，而 DSH 自己不敢删。

排查只要三步：读锁里的 PID → `tasklist` 查它是否还活着 → 死了就删。

> 这条也解释了主人遇到过的"双击打不开"—— 根因往往不是程序坏了，是那把没人管的锁。
> 教训：**别用"跑一次测试"的方式去碰 DSH 内核**，进程被掐断就留下孤儿锁。

→ 详见 [dsh/02-写锁与孤儿锁.md](../dsh/02-写锁与孤儿锁.md)

## 5. GitHub 主站不通的两条绕行路

实测（**绕开沙箱代理**后才是真实网络）：

| 目标 | 结果 |
|---|---|
| `github.com` | **21 秒超时，被墙** |
| `api.github.com` | 0.5 秒 ✅ |
| `registry.npmjs.org` | 1.1 秒 ✅ |

于是出现了"主站不通但 API 通"的组合。两条绕行路：

**路 A：让 git 走镜像**（装 GitHub 上的插件必需，因为 `dsh plugin add github:...` 内部就是 `git clone`）

```bash
git config --global url."https://gh-proxy.com/https://github.com/".insteadOf "https://github.com/"
```

用**全局配置**而非环境变量的原因：桌面版会清洗子进程的环境变量，env 注入在它自带的插件市场里不生效。
好在仓库里记录的 remote 仍是原始 github.com 地址 —— 它只改传输层，不动数据。

**路 B：把 MCP 从远端 HTTP 换成本地 stdio**

远端端点单次握手要 2.7~6.8 秒，而 MCP 客户端的连接超时**硬编码、不可配置**，
首次经常赶不上 → 退避重连 → 启动白等 20 秒。换本地 stdio 后握手在本机毫秒级完成。

→ 详见 [toolbox/02-GitHub主站不通的绕行.md](../toolbox/02-GitHub主站不通的绕行.md)

## 6. 方法论：今天纠正的两个思维误区

### 6.1 「验证」要验到真正的执行层

`--dump-config` 这类"组合配置"的命令**只拼配置、不 import 模块**，
所以"配置组装成功"完全不等于"插件能用"。

**真正的验证是让代码跑起来**：逐个 `import` 插件入口、逐个执行 client 脚本。
今天就是靠这个才发现坑 B 的（之前的"验证通过"是假的）。

### 6.2 测网络前先确认自己走的是哪条路

这台机器的 shell 里有沙箱注入的 `http_proxy=http://127.0.0.1:52524`
（**不是**用户级变量，已用注册表核实过）。也就是说：

**所有不带 `--noproxy '*'` 的 curl 测出来的延迟都是代理的，不代表真实网络。**

改之前我测出"GitHub 端点 2~7 秒"，改之后才发现真实网络另有答案。
**测量本身也要先排除干扰项。**

## 7. 今日新增的可复用工具

| 工具 | 作用 |
|---|---|
| `E:\DSH\tools\verify-plugins.mjs` | 逐个动态 `import` 插件 **host 半**入口，报 OK/FAIL |
| `E:\DSH\tools\verify-client-ids.mjs` | 离线复现 client 模块表：真执行每个 `client.js`，核对注册 id 是否等于包名 |
| Windows 回收站删除 | `[Microsoft.VisualBasic.FileIO.FileSystem]::DeleteFile($p,'OnlyErrorDialogs','SendToRecycleBin')` |

**两个验证脚本要配着用** —— host 半和 client 半是两套加载机制，各查各的。
