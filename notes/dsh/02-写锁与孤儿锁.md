# DSH 的写锁与"孤儿锁"：为什么程序会突然永久打不开

> **日期**: 2026-09-14
> **标签**: #DSH #DeepSeekHarness #文件锁 #排错 #启动失败 #踩坑
> **状态**: 🟢 已整理

## 我要解决什么问题

DSH 突然打不开，日志里反复出现同一句：

```
Error: atomic-write: timed out waiting for the writer lock
  at E:\DSH\home\profiles\node_modules.lock
```

重试没用，重启电脑也未必有用。但它不是"程序坏了"——
**问题全在那一个几十字节的锁文件上**。

## 核心概念

### DSH 的写锁是怎么工作的

读 `@deepseek-ai/dsh-atomic-write` 的源码，规则非常明确：

| 设计点 | 具体行为 |
|---|---|
| 创建方式 | 用 `wx`（独占）模式创建 `<文件名>.lock` |
| 锁的内容 | **里面写的是持有人的 PID**（就是一个进程号） |
| 等待时长 | **只等 2000 毫秒**，超时就报错 |
| 自动清理 | **没有**。永不自动清理 |

### 为什么"永不自动清理"是故意的

源码注释写了原因，原话：

> *"The contender never removes an existing lock because **file age cannot prove that
> its owner stopped**; orphan recovery is an operator action."*

翻译一下这个设计逻辑：

- 看到一把锁很旧，**不能推断它的主人已死** ——
  也许那个进程只是被挂起了、也许它正在写一个很大的文件
- 如果锁"看起来旧就删"，就会出现**两个进程同时写同一份配置**的局面，
  结果可能比"打不开"严重得多（配置损坏）
- 所以作者宁可**卡住等人来处理**，也不冒险自动删

**"operator action" = 由人来判断和处理。** 这句话就是官方给的操作指引。

### 孤儿锁是怎么产生的

**占锁的进程被强杀，锁留在原地。** 常见原因：

- 程序崩溃
- 任务管理器里"结束进程"
- 命令行超时掐断（`timeout 300 dsh ...` 这类）
- 从脚本/沙箱里跑，父进程回收时把子进程一起带走

这时锁文件里记的 PID **已经不指向任何活着的进程**，但文件还在，
于是**后续每一次启动都在等一个永远不会释放的锁**。

> 一句话：**孤儿锁 = 锁的主人已经死了，但锁还在。**

### 为什么表现是"只等 2 秒"

因为等待只有 2000ms，所以症状永远是**秒失败**，不是卡住不动。
看到"等了两秒就报锁超时"，基本可以直接往这个方向查。

## 排查方法（三步）

### 第 1 步：看锁里是谁

```bash
cat "E:\DSH\home\profiles\node_modules.lock"
# 输出一个 PID，比如 235076
```

顺便看看文件时间 —— 它能告诉你这把锁是"刚刚产生的"还是"放了很久"：

```bash
ls -la "E:\DSH\home\profiles\node_modules.lock"
```

### 第 2 步：查这个 PID 还活着吗

```cmd
tasklist /fi "PID eq 235076"
```

- 提示"没有运行的任务匹配指定标准" → **就是孤儿锁** ✅
- 能列出来 → 说明真有进程在占，**别删**，先搞清楚它是什么

> 小坑：`tasklist` 加了 `/nh` 时表头会消失，输出格式不同，判断脚本容易误判。
> 稳妥做法是直接看输出里**有没有真的出现那个进程名**。

### 第 3 步：确认是孤儿就删掉

```cmd
del E:\DSH\home\profiles\node_modules.lock
```

**删完等几秒再确认一次没被重建** —— 如果又被创建出来，说明确实有活进程在占，
那就是另一个问题了。

## 示例：一次真实的诊断

```
锁里的 PID     →  235076
tasklist 查询  →  该 PID 不存在（已死）
锁文件时间     →  19:22（37 分钟前）
当时在跑的进程 →  只有 PID 228128（网页版服务）和 PID 221240（桌面版主进程）
结论           →  235076 两个都不是，是孤儿锁，删除
```

删掉后立刻正常，且 8 秒内没有被重建 —— 确认释放干净。

## 踩坑记录

| 问题 | 原因 | 解决 |
|---|---|---|
| 只等 2 秒就报"写锁超时" | `wx` 创建的锁 + 2000ms 超时 | 查是孤儿锁还是有活进程 |
| 锁住了但不知道是谁 | 锁里其实**就写着 PID** | `cat` 一下这个 `.lock` 文件 |
| 删了又出现 | 说明真有活进程在占 | 别再删了，去查那个 PID 是什么 |
| 以为"锁 = 只能跑一个实例" | 锁是**按单次操作获取/释放**的，不是长期占用 | 正常的多入口可以共存；卡住是别的原因 |
| 强杀程序后下次启动失败 | 强杀不走清理逻辑 → 留孤儿锁 | 尽量正常退出；出问题按三步处理 |
| **用脚本跑一次测试就留下锁** | 脚本被超时/SIGTERM 掐断 | **别用"跑测试"的方式碰程序内核**；测试后检查锁 |

## 最重要的那条教训

**"我跑个测试验证一下" 这种操作，可能就是下一次"打不开"的成因。**

今天这台机器上就是这样：为了验证配置能加载，用沙箱跑了一次内核，
进程被掐断 → 留下孤儿锁 → **下一次主人双击桌面版时正好撞上，报"打不开"**。

所以现在的规矩是：**碰这类带写锁的程序，测试要么在它正常退出的前提下做，
要么测试完立刻按三步检查锁。** 宁可少测一次，也别留一把锁给未来的自己。
