# DSH 插件为什么会让整个界面打不开：双半结构与三个致命坑

> **日期**: 2026-09-14
> **标签**: #DSH #DeepSeekHarness #插件 #排错 #Electron #踩坑
> **状态**: 🟢 已整理

## 我要解决什么问题

装完 9 个插件后，DSH 桌面版**窗口能打开，但整页只显示一行**：

```
Failed to load plugins
failed to import loader entry 80536348 (dsh-filetree): client modules
/plugin:///?@deepseek-ai/dsh-api-gateway/client.js, ...(一长串模块路径)
```

**一个插件出问题，整个界面都废了。** 而且 `logs\host\*.log` 里干干净净，什么错误都没有。

这篇是把它彻底拆开搞明白的记录。

## 核心概念

### 1. DSH 插件是"双半"结构

| | host 半 | client 半 |
|---|---|---|
| 跑在哪 | Node（服务端） | 浏览器（渲染进程） |
| 入口 | `main` / `exports["."]` | `exports["./client"]` |
| 干什么 | 注册数据接口、服务端逻辑 | 画界面、调接口 |
| 报错写哪 | `logs\host\*.log` | 渲染进程控制台（**不落盘**） |

两边**各有一套独立的加载机制**，所以"host 半没问题"完全不代表"插件能用"。

### 2. client 半的加载流程（关键）

1. host 端**按包名**扫出要加载的模块，拼成一个合并请求：

   ```js
   function comboUrl(ids, rev, ...) {
     return `/plugins/??${ids.map(id => `${id}/client.js`).join(",")}&rev=${rev}`;
   }
   ```

2. 浏览器执行每个 `client.js`，脚本用下面这种方式**登记自己**：

   ```js
   window.__ModuleLoader__.load({
     id: "dsh-filetree",              // ← 这个 id 必须等于包名！
     factory: (require) => { ... }
   });
   ```

3. 回到加载器核对（`dsh-client-modules/lib/client.js`）：

   ```js
   if (!this.factories.has(id))
     throw new Error(`client-modules: bundle ${url} loaded without registering "${id}"`);
   ```

**注意第 1 步和第 2 步用的是同一个名字：包名。** 对不上就抛错。

### 3. 插件要"激活"还需要一个声明

DSH 只把**声明了 `dsh.bundle.patch`** 的包加进 profile 的层栈：

```js
// dsh/lib/plugin-*.js
function exportsPatch(packageName, profileDir) {
  return readProfileManifest(NAME, dir).dsh?.bundle?.patch !== void 0;
}
// reconcilePlugins(): 只有 exportsPatch 为真的依赖才会进 dsh.profile.bundles
```

没有这个声明的包，`dsh plugin add` 只会把它当**普通依赖**装上，并给一句警告：

```
dsh: warning: <包名> declares no dsh.bundle — installed as a plain dependency,
  not a profile layer (a later update that gains one activates it automatically)
```

## 三个致命坑（今天全踩了）

### 坑 A：host 半的入口文件根本不存在

**症状**

```
plugin tree failed to load: failed to import loader entry config-manager (dsh-config-manager):
Cannot find module '...\node_modules\dsh-config-manager\lib\index.js'
```

**原因**：`dsh-config-manager` 的 GitHub 仓库**只有 TypeScript 源码**，
`main` 指向 `./lib/index.js`，而 `lib/` 要靠 `build` 脚本生成。
pnpm 装 git 依赖时会按仓库的 `files` 字段过滤，**连 tsconfig 都没拉下来** ——
既构建不了、也没有产物。

**修法**：改用 npm 源（npm 上的包带预编译 `lib/`）：

```bash
dsh plugin --profile web remove dsh-config-manager
dsh plugin --profile web add dsh-config-manager      # 去掉 github: 前缀，走 registry
```

### 坑 B：client 半注册的 id 和包名不一致

**症状**：整页 `Failed to load plugins`，**host 日志完全干净**。

**原因**：`github:lak321/dsh-filetree@0.2.0` 打包出来的 client 代码里写的是：

```js
window.__ModuleLoader__.load({
  id: "@deepseek-ai/dsh-client-ui-filetree",   // ← 写成了内置包的名字
  ...
});
```

它自己叫 `dsh-filetree`，却登记成别的名字 → 核对 `factories.has("dsh-filetree")` 为假 → 整棵树挂掉。

**修法**：换成 id 正确的版本。本例换成了 npm 上的 `dsh-filetree@0.3.0`
（**另一个作者的另一个项目**，功能还更全）。

### 坑 C：包装上了，但没被激活

**症状**：`dsh plugin add` 显示成功，`package.json` 的 `dependencies` 里有它，
但 `dsh.profile.bundles` 里**没有**，插件不工作。

**原因**：见上面第 3 点 —— 没有 `dsh.bundle.patch` 声明。

**修法**：在 profile 的补丁层手动补一条 host 入口
（`<DSH_HOME>\profiles\<profile>\cordis.patch.yml`）：

```yaml
- insert:
    - id: filetree
      name: 'dsh-filetree'      # name 必须等于包名
```

> `id` 和 `name` 允许不同 —— 参考官方生态里的写法：
> `id: dream-skin` / `name: 'dsh-dream-skin'`。
> 但 **`name` 必须等于包名**，因为 client 那边也按包名核对。

## 排查方法（怎么定位是哪一个坑）

```
第 1 步：看界面报的 entry 名字 —— 它就是包名
        （例："(dsh-filetree)" → 去查这个包）

第 2 步：查 host 半入口文件是否存在
        → 不存在 = 坑 A

第 3 步：host 半存在但界面打不开 → 大概率是坑 B
        写个脚本离线复现 client 模块表的核对逻辑（见下）

第 4 步：插件"装上了但不工作"→ 查 dsh.profile.bundles 里有没有它 = 坑 C
```

### 为什么"配置组装成功"不算验证

```bash
dsh --profile web --dump-config     # 只组合配置，不 import 模块
```

这条命令**跑通不代表插件能用** —— 坑 A 就是它通过、但模块加载失败的。
必须**真的把代码 import 一遍**。

### 两个必须配着用的验证脚本

| 脚本 | 验证对象 | 原理 |
|---|---|---|
| `verify-plugins.mjs` | **host 半** | 读 profile 的 bundles，逐个动态 `import` 入口文件 |
| `verify-client-ids.mjs` | **client 半** | 造一个 `window.__ModuleLoader__`，真执行每个 `client.js`，核对注册 id 是否等于包名 |

后者是这次专门写的，因为**前者查不出坑 B**。

## 踩坑记录

| 问题 | 原因 | 解决 |
|---|---|---|
| 界面报错但 host 日志干净 | client 半的报错只在渲染进程，不落盘 | 别只盯 `logs\host\`；用离线脚本复现 |
| `--dump-config` 通过但插件不工作 | 它不 import 模块 | 用真的 import 来验证 |
| 从 GitHub 装插件后整个应用起不来 | 仓库没提交构建产物 | **装之前先确认 `main`/`exports` 指向的文件在仓库里真实存在** |
| 插件装了却不见效 | 没有 `dsh.bundle.patch`，没进 bundles 层栈 | 手动在 profile 的 `cordis.patch.yml` 里 insert |
| 一个插件坏了整页打不开 | 插件树是整体加载的，一个 entry 失败就全挂 | 装完新插件先跑两个验证脚本再重启 |
| 同名包其实是不同项目 | npm 和 GitHub 上可能有两拨人做同名插件 | 装之前看清作者和仓库地址 |

## 安全提醒

装第三方插件 = **在本机运行别人的代码**。挑的时候至少看：

- 有没有 star、有没有 CI/测试
- `main` / `exports` 指向的文件在不在
- 有没有可疑的 `postinstall` / `prepare` 构建脚本
- 用途是否单一（一个包干一件事的，比"全能包"好审）
