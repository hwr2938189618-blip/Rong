# [方案] 多 AI 共写仓库的防冲突方案（决策记录）

> **日期**: 2026-09-16
> **标签**: #GitHub #多AI协作 #冲突避免 #决策记录
> **状态**: 🟢 已整理

## 我要解决什么问题

本机有**三个 AI 助手**（DSH / WorkBuddy / Codex）在写同一个仓库 `hwr2938189618-blip/Rong`。参与者越多，同时改同一个文件（尤其 `notes/README.md`、`README.md`、`AGENTS.md` 这类共享文件）的概率越高。

**2026-09-16 已经真实撞过一次**：我和 WorkBuddy 在同一分钟内各推了一次 `notes/README.md`（我 04:51:59，它 04:53–04:54）。结果没丢内容——**因为它是后发，以我的版本为底座叠加**。但那是运气，不是机制。

这篇笔记把可选方案记下来备查，**现在不实施**。

## 核心概念

### 现状：靠自觉，没有技术强制

当前唯一约束是 `AGENTS.md` 里的四条"防覆盖铁律"：

1. 推送前先 `get_file_contents` 拉目标文件最新版
2. 共享文件改前必拉最新
3. 推完回读验证（分类计数 vs 实际文件数、有没有覆盖别人的改动）
4. 学别家做法时注意路径归属

**漏洞**：全靠每个 AI"记得去做"。只要有一个不照做，或两个 AI 在**同一秒**都读完旧版本再各自推，后推的那个就会静默覆盖先推的。GitHub 的 `push_files` 不带乐观锁（除非用 `sha` 参数做条件更新），所以**不会报错**。

### 方案 A：轻量写锁约定（LOCK 标记文件）

改共享文件前，先在仓库里放一个锁标记，改完删掉。

```
流程：
1. 读 notes/_locks/README.md 或直接查锁文件是否存在
2. 不存在 → 写 notes/_locks/<助手名>.lock（内容是时间 + 意图）
3. 拉最新版 → 改 → 推 → 删锁
4. 存在但他人的锁 → 等，或改推非共享文件的部分
```

| | 说明 |
|---|---|
| ✅ 优点 | 改动很小，任何 AI 都能实现（不依赖 git）；共享文件的"抢"变成串行 |
| ❌ 缺点 | 仍是自觉：崩溃/中断会留死锁，需要"超时视为失效"规则；多一次 commit（放锁+删锁） |
| ⚠️ 关键 | 必须规定 **锁过期时间**（如 10 分钟），否则中断一次就卡死别人 |

### 方案 B：本地 git 仓库 + 正常 push（最稳）

把 `E:\DSH\workspace\Rong` 变成**真正的 git 仓库**（现在只是文件副本，没有 `.git`），所有 AI 都走 `git pull → 改 → commit → push`。冲突由 git **明确报错**，而不是静默覆盖。

| | 说明 |
|---|---|
| ✅ 优点 | 冲突**必然被发现**（non-fast-forward / merge conflict），不可能静默丢内容；有完整历史可回溯 |
| ⚠️ 前提 | `github.com` 主站不通（21 秒超时）→ 需要解决传输：目前 `.gitconfig` 里已配 gh-proxy 镜像，**只读（clone/ls-remote/fetch）实测可用；写（push）未验证** |
| ❌ 缺点 | 每个 AI 都要改成 git 工作流（WorkBuddy 侧现成的 `publish.py` 走的是 REST，得改）；首次要 clone 全仓 |
| 次选 | 不用远端 push，改为"本地 git 仓库 + 各自 commit"，由人来 `git merge` 并推送 |

### 方案对比

| 维度 | 现状（自觉） | A：写锁 | B：git |
|---|---|---|---|
| 防静默覆盖 | ❌ | 🟡 大部分 | ✅ 强制 |
| 实施成本 | 0 | 低（约定 + 一次 commit） | 中（改工作流） |
| 中断后遗症 | — | 可能留死锁（需超时规则） | 无 |
| 历史可回溯 | 靠平台 commit | 靠平台 commit | ✅ 本地完整 |
| 依赖 | 无 | 无 | git + 传输通道 |

### 建议的采用时机

- **现在**：维持现状（自觉 + 回读验证），因为冲突频率还低（三个 AI 不同时开工）
- **出现下列任一情况就升级到 B**：
  - 一周内 ≥2 次"同时改同一文件"
  - 发生过一次真实的静默覆盖（内容丢失）
  - Codex 接入后三方并发变常态
- **A 作为 B 之前的过渡**：若只是偶尔撞车，加锁比改工作流便宜

## 示例代码

方案 B 的落地骨架（供以后实施参考）：

```bash
# 1) 把文件副本变成真仓库（首次）
cd /e/DSH/workspace
git clone https://github.com/hwr2938189618-blip/Rong.git Rong-git

# 2) 日常流程：先拉后改再推，让 git 自己拦冲突
git -C Rong-git pull --rebase
# ... 修改文件 ...
git -C Rong-git add -A && git -C Rong-git commit -m "笔记: 新增《标题》"
git -C Rong-git push        # 冲突会在这里报 non-fast-forward，而不是静默覆盖

# 3) 若 push 走不通（github.com 主站被墙），先验证镜像是否支持写：
git config --global --get-regexp '^url\.'   # 应看到 gh-proxy 重写
```

方案 A 的超时规则（伪代码）：

```
读到他人的锁：
  若 now - 锁时间 > 10 分钟 → 视为死锁，可覆盖并注明
  否则 → 本次只改非共享文件，或等待
```

## 踩坑记录

| 问题 | 原因 | 解决 |
|---|---|---|
| 以为"后推的会报冲突" | `push_files`/REST 是无条件写，没有乐观锁 | 要么先读最新版，要么用带 `sha` 的条件更新 |
| 以为现在有机制保障 | 实际只有 `AGENTS.md` 的自觉约定 | 想强制就得换方案 B（git） |
| `E:\DSH\workspace\Rong` 以为是仓库 | 它只是**文件副本，没有 `.git`** | 真仓库在 `E:\workbuddy文件夹\2026-09-12-13-13-38\Rong-repo` |
| gh-proxy 能 clone 就以为能 push | 只读与写入走的校验不同 | **写未验证**，别假设 |
