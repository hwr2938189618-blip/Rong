## 核心概念

### 1. 载体分工：什么内容存哪

不是所有东西都该进仓库。仓库是给人回头看的，记忆库是给 AI 用的，混在一起两边都难受。

| 内容类型 | 存哪 | 进仓库吗 |
|---|---|---|
| 短事实 / 偏好 / 决策 | AI 的记忆库 | ❌ |
| 成套流程 / 方法论 / 命令模板 | 技能目录 `skills/` | ✅ 镜像 |
| 大块资料 / 教程 / 代码片段 | 笔记 `notes/<分类>/` | ✅ |
| 必须长期遵守的规矩 | 助手的指令文件 | ✅ 一并提交 |

判断标准很简单：**"这条以后还要反复查吗？"** 要 → 进仓库；只是这一轮用一下 → 记忆库。

### 2. 两个助手对接同一个仓库，通道却不一样

这是这次最容易踩空的地方——同一个仓库，两个助手走的路**完全不同**：

| | WorkBuddy | DSH |
|---|---|---|
| 可用工具 | ❌ 无 `mcp__github__*` | ✅ 本地 stdio 的 `mcp__github__*` |
| 推送方式 | **REST API 手工六步**（技能 `github`） | `mcp__github__push_files` |
| 最终出口 | `api.github.com` | `api.github.com` |

> ⚠️ DSH 侧的 `AGENTS.md` 里写着"一律走 MCP `push_files`，不要试 gh CLI"——
> 这条**只在 DSH 里成立**。WorkBuddy 里根本没有那个 MCP，照搬会卡住，
> 正确做法是走 REST API。

好在两条路的**底层出口是同一个** `api.github.com`，所以只要网络通，两边都能推。

### 3. 网络事实（本机实测）

| 目标 | 结果 |
|---|---|
| `api.github.com` | ✅ 通，1.07 秒 |
| `github.com` 主站 | ❌ 直连超时（被墙），看网页要 VPN |
| `git ls-remote`（经 gh-proxy 重写） | ✅ 能读到 `refs/heads/main` |
| `gh` CLI | 装着，但**从未登录**（登录走主站，所以别试） |

`.gitconfig` 里有一条全局重写，把 `github.com` 的 git 流量导到 gh-proxy：

```
url.https://gh-proxy.com/https://github.com/.insteadOf = https://github.com/
```

所以**只读**（clone / ls-remote / fetch）可以借它绕过去；**写入**（push）不确定，
稳定做法还是 REST API。

## 示例代码

Git Data API 六步，一次提交能带多个文件、只产生一个 commit：

```python
# 1. 拿分支当前 head
ref = call('GET', f'{API}/git/ref/heads/main')
head_sha = ref['object']['sha']
# 2. 拿 head 对应的 tree 作为底
base_tree = call('GET', f'{API}/git/commits/{head_sha}')['tree']['sha']
# 3. 每个文件建 blob（base64）
# 4. 建新 tree —— 必须带 base_tree！
tree = call('POST', f'{API}/git/trees', {'base_tree': base_tree, 'tree': items})['sha']
# 5. 建 commit
commit = call('POST', f'{API}/git/commits',
              {'message': msg, 'tree': tree, 'parents': [head_sha]})
# 6. 移动分支引用
call('PATCH', f'{API}/git/refs/heads/main', {'sha': commit['sha'], 'force': False})
```

完整可跑脚本在技能 `github` 的 `references/api-file-push.md`。

## 踩坑记录

| 问题 | 原因 | 解决 |
|---|---|---|
| 推送后仓库原有文件全没了 | 建 tree 时没传 `base_tree` | **必须传 `base_tree`**，它以父 tree 为底再叠加本次改动 |
| `git -C /e/DSH/...` 报 `No such file or directory`，但 `ls` 明明能看到 | `git.exe` 是 Windows 原生程序，收到 MSYS 路径 `/e/...` 会被错拼成 `e:\e\...` | 传给原生程序的路径写 `E:/DSH/...`；MSYS 自带命令才用 `/e/...` |
| Bash 里 `dirname` / `head` / `ls` 全 `command not found` | WorkBuddy 桌面版 Bash 的默认 PATH 是坏的 | 每条命令开头先 `export PATH="/c/Users/29381/.workbuddy/binaries/PortableGit/versions/1.2.0/usr/bin:.../bin:$PATH"` |
| 以为 `E:\DSH\workspace\Rong` 是仓库，`git status` 却报不是 git 仓库 | 那只是**一份文件副本**，没有 `.git` | 真正的本地镜像在 `E:\workbuddy文件夹\2026-09-12-13-13-38\Rong-repo`；不想搞混就直接不存本地，每次从 API 拉 |
| token 读出来认证失败 | 记事本存成了 UTF-8 with BOM | 用 `encoding='utf-8-sig'` 打开 |
| `gh auth status` 一直失败 | gh 登录走 `github.com` 主站，本机不通 | 别反复试 device flow，直接切 REST API |

## 本机落地位置

规矩要落地，得知道东西都放在哪：

| 东西 | 在哪 |
|---|---|
| WorkBuddy 侧技能（含一键提交脚本 `publish.py`） | `C:\Users\29381\.workbuddy\skills\rong-notes-publish\` |
| DSH 侧技能 | `E:\DSH\home\skills\github-repo-push\` |
| 本地镜像 | `E:\workbuddy文件夹\2026-09-12-13-13-38\Rong-repo` |
| 令牌 | 环境变量 `GITHUB_PAT_TOKEN`（文件在 `D:\codex\token\token.txt`，**绝不打印、绝不提交**） |

脚本用法：

```bash
python publish.py --base <本地基准目录> --message "笔记: 新增《标题》" \
    --file notes/README.md --file "notes/toolbox/06-标题.md"
```

它自动走完六步并**回读验证**（commit 在、文件在、字节数一致、根目录原有文件没丢）。
