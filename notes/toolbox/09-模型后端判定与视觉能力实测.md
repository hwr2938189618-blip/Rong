# 模型后端判定与视觉能力实测

> **日期**: 2026-10-03
> **标签**: #模型后端 #DeepSeek #视觉能力 #配置排查 #踩坑
> **状态**: 🟢 已整理

## 我要解决什么问题

两个问题：

1. **"现在跑的是哪个模型、哪个版本？"** —— 模型自述不可靠，得去读配置 + 拿官方接口实测
2. **配了个 `supportsImages: true`，这个开关到底有没有让图片真的走通？** —— 声明不等于可用

## 核心概念

### 一、模型自述不可信，三层配置的权威性要分清

| 层 | 位置 | 说明 |
|---|---|---|
| 本地声明 | `~/.workbuddy/models.json` | 手写的自定义模型条目（id / name / 能力开关） |
| **服务端下发（最权威）** | `~/.workbuddy/cache/acc-product-config-v3.json` 的 `models[]` | 内置 + `custom-local:` **合并后的最终生效目录** |
| 会话状态 | `app/session/Local Storage/leveldb/` 的 `cb-newtask:model:<会话id>` | 当前会话选了哪个，App 自己管 |

判断"改动有没有生效"，要读**第二层**——第一层只是输入，第二层才是结果。

### 二、"直连"和"走网关"是两条路，别混为一谈

同一个底层模型可能有两处入口：

| | 自建直连 | 内置（走平台网关） |
|---|---|---|
| 形式 | `custom-local:<id>` 直连厂商 URL | 平台下发的内置条目 |
| 计费 | **自己的 API 账户余额** | 平台 credits |
| 认出方式 | 出现在 `models.json` | 出现在服务端配置的 `models[]` |
| 能否无头实测 | ✅ 能（直接打厂商 API） | ❌ 不能（私有网关接口） |

⚠️ **一条重要认知**：如果两边是同一个底层模型，那"自建直连"的额外价值可能只有输出上限和档位可选性——**别急着建议用户切换，那是替人做花钱的决定**。给对照数据，让用户选。

### 三、视觉能力必须实测，不能看声明

| 状态 | 表现 |
|---|---|
| 真支持 | 能逐字读对图里的文字 |
| **假支持** | **请求返回 200、内容看着正常，但图片被静默丢弃**，替换成 `[Unsupported Image]` 占位符 |
| 不支持 | 明确报错 |

**假支持不会以 4xx 暴露**，最容易被骗过去。必须核实模型是不是真读到了图里的内容。

## 示例代码

### 判定实际生效的模型

```python
import json, os
p = os.path.expanduser('~/.workbuddy/cache/acc-product-config-v3.json')
d = json.load(open(p, encoding='utf-8'))
for m in d.get('models', []):
    if 'deepseek' in str(m.get('id', '')).lower():
        print(m.get('id'), '|', m.get('name'), '| img =', m.get('supportsImages'))
```

### 拿官方接口要清单

```bash
curl -s https://api.deepseek.com/models -H "Authorization: Bearer $KEY"
```

报错信息本身就有价值——它会**直接列出可用 ID 白名单**，等于一次权威枚举。

### 视觉能力决定性测试

```python
import base64, json, urllib.request
b64 = base64.b64encode(open(src, 'rb').read()).decode()
payload = {"model": "deepseek-flash", "max_tokens": 900,
  "messages": [{"role": "user", "content": [
    {"type": "text", "text": "逐行读出这张截图里的所有文字，原样输出。"},
    {"type": "image_url", "image_url": {"url": "data:image/png;base64," + b64}}]}]}
req = urllib.request.Request('https://api.deepseek.com/chat/completions',
  data=json.dumps(payload).encode(),
  headers={'Content-Type': 'application/json', 'Authorization': 'Bearer ' + KEY})
d = json.load(urllib.request.urlopen(req, timeout=90))
print(d['choices'][0]['message'].get('content'))
```

**测试素材的选择就是方法本身**：不要用纯色图——那是模型瞎猜也能中的。要用**它不可能猜到的内容**（例如一张包含配置界面文字的截图）。

## 踩坑记录

| 问题 | 原因 | 解决 |
|---|---|---|
| 拿纯色图测视觉，得出"支持"的结论 | 纯色图瞎猜也能中，证明不了任何事 | **测试素材必须"不可猜"**，用含具体文字的截图 |
| 第一次实测 `content` 返回空字符串，差点判成"不支持" | `max_tokens` 只给了 60，思考型模型的输出全被 reasoning 吃掉 | `max_tokens` 给足（≥900），否则会把"输出被截断"误判成"没有视觉能力" |
| 用"逐字严格相等"校验 OCR 结果，判成模型不稳定 | 3 次输出内容全对，但格式在抖（多一行前言、多个占位符） | 校验**语义命中**，别用严格相等 |
| 把前端显示的模型 ID 当"假 ID" | 混淆了"直连"与"走网关"两条路 | 前端显示 ID 可能是平台内置条目，只是不能直连厂商 API |
| 改完配置以为立刻生效 | 会话存储里还记着旧 key，形成悬空引用 | 改 ID 后要**重启 + 在模型选择器里重选**；App 重启时自己做 leveldb 压缩会清掉悬空键 |
| 想手工改 leveldb 去修悬空引用 | App 运行时动它的数据库容易冲突 | **状态归 App 自己管，重启即自愈**，别手工改 |
| 配了 `supportsImages: true` 就以为图片能走通 | 那只是个开关声明 | 必须实测端到端，见上 |
